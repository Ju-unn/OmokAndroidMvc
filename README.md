# 오목 (Omok) — Android

렌주룰 오목 게임 Android 앱입니다. 콘솔(IntelliJ) 프로젝트를 Android Studio로 옮겨왔고,
MVC 패턴 학습을 목표로 합니다.

## 현재 구조 (MVC)

```
omok/
 ├─ domain/      게임 규칙 (보드, 승리 판정, 렌주룰 금수 판정) — 순수 Kotlin, Android를 모름
 ├─ controller/  View의 터치 이벤트를 domain에 전달하고 결과를 UI 상태로 반영
 └─ view/        Compose로 보드를 그리고 터치를 Position으로 변환
```

- **Domain**: `OmokGame`이 규칙의 입구. "여기 둘 수 있어?", "이겼어?"를 전부 도메인이 판단한다.
- **Controller**: `GameController.onCellClick(position)` — 판단하지 않고 도메인에 묻고, 결과만 `GameUiState`로 노출한다.
- **View**: `OmokScreen` — `uiState`를 그리기만 하고, 문구(흑/백, 에러 메시지) 선택도 View의 몫.

## 다음 목표 (추가할 기능)

1. **이어하기** — 앱을 재시작해도 하던 게임을 다시 시작할 수 있다.
2. **게임방** — 게임방(저장 슬롯)을 만들고 입장할 수 있다. (한 폰에서 여러 판 관리)
3. **전적** — 사용자별로 게임 기록(승/패)을 관리할 수 있다.

## 설계

### 아키텍처: Model에 데이터 계층이 추가된다

```
[View] ←→ [Controller] ←→ [Domain (게임 규칙)]
                ↕
          [Repository] ←→ [Room DB (폰 안의 데이터베이스)]
```

- **Repository**: "저장해줘/불러와줘"만 담당하는 클래스. Controller는 저장 방식(Room인지
  파일인지 서버인지)을 몰라도 된다. 나중에 온라인 대전으로 확장할 때 이 뒤쪽만 갈아끼운다.
- **Domain은 변경하지 않는다.** 게임 규칙은 "저장"이라는 개념을 몰라야 한다.

### DB 테이블 3개

| 테이블 | 컬럼 | 역할 |
|---|---|---|
| `UserEntity` | id, 이름 | 로그인 없는 로컬 프로필 |
| `GameRoomEntity` | id, 방 제목, 흑 사용자 id, 백 사용자 id, 상태(진행중/종료), 승리한 돌, 생성 시각 | 저장 슬롯 = 게임방 |
| `MoveEntity` | id, 방 id, 몇 번째 수, 위치("H8") | 돌을 놓은 순서 기록 |

> 클래스 이름에 `Entity`를 붙이는 이유: DB의 `GameRoomEntity`와 Room 라이브러리 자체,
> 그리고 domain의 `Row`/`Column` 같은 이름들이 서로 충돌하지 않게 구분하기 위해서다.

**설계 결정 두 가지 (왜 이렇게 하는가):**

1. **보드(15×15)는 저장하지 않는다.** 수순(돌을 놓은 순서)만 저장한다.
   방에 입장할 때 `OmokGame.create()`로 새 게임을 만들고 저장된 수순을 순서대로
   `placeCurrentStone()`으로 다시 두면 보드가 완벽히 복원된다.
   → domain을 한 줄도 안 고치고 저장/복원이 된다.
2. **전적 테이블은 만들지 않는다.** "철수의 승수"는 `상태=종료이고 승리한 돌이 철수 쪽인
   방의 개수`를 세면 나온다. 계산으로 구할 수 있는 값은 저장하지 않는다.
   (저장하면 원본과 어긋날 위험이 생긴다 — DB 설계의 기본 원칙)

### 화면 흐름 (4개 화면)

```
[사용자 관리] ──→ [방 목록] ──→ [게임 화면 (기존 OmokScreen)]
                    └──→ [전적 보기]
```

화면 전환은 라이브러리 없이 "현재 화면" 상태값 하나로 관리한다.
(Android 표준인 Navigation Compose는 다음 학습 단계로 남겨둔다)

## 구현 계획 — 커밋 1개 = 학습 1개

각 단계는 커밋 하나로 끝나고, 매 단계에서 빌드가 통과하는 상태를 유지한다.

### 1단계: Room·KSP 의존성 추가
- **만드는 것**: gradle에 Room 라이브러리와 KSP 플러그인 추가
- **왜**: Room은 SQLite(폰 내장 DB)를 쉽게 쓰게 해주는 공식 라이브러리.
  KSP는 Room이 `@Entity` 같은 표시(어노테이션)를 읽고 실제 DB 코드를
  빌드 시점에 자동 생성해주는 도구다.
- **배우는 것**: 버전 카탈로그(libs.versions.toml)에 라이브러리 추가하는 법

### 2단계: UserEntity + UserDao
- **만드는 것**: 사용자 테이블 정의(`@Entity`)와 사용자 쿼리 모음(`@Dao`)
- **왜**: `@Entity` 클래스 = 테이블 한 줄의 모양. `@Dao` 인터페이스 = "이름으로 찾기,
  전체 목록, 추가" 같은 질의를 함수로 선언하면 Room이 구현을 만들어준다.
- **배우는 것**: Entity, DAO, `suspend` 함수(DB 작업은 화면을 멈추지 않게 백그라운드에서)

### 3단계: GameRoomEntity·MoveEntity + DAO
- **만드는 것**: 게임방·수순 테이블과 쿼리
- **왜**: 방(슬롯)과 수순이 이번 기능의 핵심 데이터. 외래키(FK)로
  "이 수순은 이 방의 것"이라는 관계를 DB에 알려준다.
- **배우는 것**: 테이블 사이의 관계(외래키), 정렬 조회(`ORDER BY 수순 번호`)

### 4단계: Database 클래스 + OmokRepository
- **만드는 것**: 테이블들을 묶는 `OmokDatabase`, Controller가 쓸 `OmokRepository`
- **왜**: Repository가 있으면 Controller는 "Room"이라는 단어조차 몰라도 된다.
  계층 분리의 핵심 — 각 층은 바로 아래층만 안다.
- **배우는 것**: Repository 패턴, 싱글턴(DB 연결은 앱에 하나만)

### 5단계: 착수 자동 저장
- **만드는 것**: `GameController`가 방 id를 갖고, 착수 성공 시 Move 한 줄 저장,
  승리 시 방 상태를 '종료'로 갱신
- **왜**: 매 수를 즉시 저장해두면 언제 앱이 꺼져도 데이터가 남는다.
- **배우는 것**: Controller에서 코루틴으로 suspend 함수 호출하기

### 6단계: 게임 복원 (이어하기)
- **만드는 것**: 방 입장 시 저장된 수순을 순서대로 다시 둬서 보드 복원
- **왜**: 목표 1(재시작 후 이어하기)이 여기서 완성된다.
- **배우는 것**: "상태 저장" 대신 "이벤트 재생"으로 복원하는 발상

### 7단계: 사용자 관리 화면
- **만드는 것**: `UserController` + 사용자 목록/추가 화면
- **왜**: 방을 만들려면 흑·백을 맡을 사용자가 먼저 있어야 한다.
- **배우는 것**: DB 목록을 Compose 리스트(LazyColumn)로 표시, 화면 상태값으로 전환

### 8단계: 방 목록 화면
- **만드는 것**: `RoomListController` + 방 만들기/목록/입장 화면, 전체 화면 전환 연결
- **왜**: 목표 2(게임방 생성/입장)가 여기서 완성된다.
- **배우는 것**: 화면 사이에 값(방 id) 전달하기

### 9단계: 전적 화면
- **만드는 것**: 사용자별 승/패/진행중 집계 쿼리 + 표시 화면
- **왜**: 목표 3(사용자별 기록)이 여기서 완성된다. 별도 테이블 없이 쿼리로 집계한다.
- **배우는 것**: 집계 쿼리(COUNT), 조건 검색

### 10단계: 시나리오 검증
- 방 생성 → 몇 수 두기 → 앱 재시작 → 이어하기 → 승리 → 전적 확인

## 용어 사전 (왕초보용)

| 용어 | 뜻 |
|---|---|
| Room | 폰 내장 DB(SQLite)를 Kotlin 클래스로 다루게 해주는 공식 라이브러리 |
| Entity | DB 테이블 한 줄의 모양을 정의한 클래스 (`@Entity`) |
| DAO | 쿼리를 함수로 선언해두는 인터페이스 (`@Dao`), 구현은 Room이 자동 생성 |
| Repository | 저장/조회만 담당하는 중간 클래스. Controller와 DB 사이의 벽 |
| suspend / 코루틴 | 오래 걸리는 작업(DB, 네트워크)을 화면 멈춤 없이 실행하는 Kotlin 문법 |
| KSP | 어노테이션을 읽고 코드를 자동 생성하는 빌드 도구 (Room이 사용) |
